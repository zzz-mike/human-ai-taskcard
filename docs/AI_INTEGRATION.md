# AI 接入指南

## 本程序与 AI 的分工

本程序为人和 AI 保存可恢复的任务状态。它没有内置大模型，不会因为运行 `serve`、`start` 或 `continue` 就自行思考和执行工作。`start` 和 `continue` 记录环境快照并改变任务状态；实际执行由已接入的外部 AI 助手完成。

| 参与方 | 职责 |
| --- | --- |
| 用户 | 明确目标、确认范围、提供必要权限、决定需要审批的操作 |
| 外部 AI 助手 | 理解需求、生成任务规格、调用工具完成工作、验证结果、通过 CLI 更新记录 |
| taskctl | 保存状态、审批、阶段记录与证据引用，检查完成条件 |
| 本地网页 | 展示任务进度和待确认事项；当前不能聊天、审批或启动 AI |

任务执行规则见 [AGENTS.md](../AGENTS.md)。这些规则需要助手遵守，程序没有能力强制拦截助手在其他工具中的行为。

## 接入前准备

1. 安装 Python 3.10 或更新版本，下载本仓库。
2. 自行选择并配置具有本地文件读写和终端执行能力的 AI 助手。模型账号、订阅、密钥与费用在该助手一侧管理，本程序不接收模型密钥。
3. 让助手打开本仓库所在目录，并明确实际任务涉及的项目路径。目录权限不能代替发布、发送等操作所需的授权。
4. 要求助手读取 README、AGENTS.md 及本指南。若助手没有自动加载项目规则文件的机制，将执行规则加入它的项目指令，或在会话中明确要求读取。

仅有模型 API 密钥仍不足以自动接入：还需要能把模型工具调用转换为本地文件或终端操作的助手或运行环境。本项目未提供该适配层，也未提供 MCP 服务、模型 SDK 集成或跨工具的安全沙箱。不同助手的兼容性需要在实际环境验证，不能把本地 CLI 测试当成所有 AI 客户端均已测试。

## 第一步：验证 AI 能访问本项目

可以将以下内容交给已配置的 AI 助手：

```text
请在当前仓库中接入人机协作任务卡。
先读取 README.md、AGENTS.md 和 docs/AI_INTEGRATION.md。
确认当前工作目录和 Python 版本，然后运行：
python3 -m taskcard.cli --help
python3 -m taskcard.cli list
告诉我实际命令结果和所用的数据目录。
暂时不要修改现有任务卡，也不要操作外部服务。
如果你不能访问本地文件或执行命令，请明确说明，不能声称已经接入。
```

看到助手真实调用工具并返回命令结果后，再进行示例演练。单纯回复“已经理解”不能证明接入成功。

## 第二步：运行虚构示例

使用独立演示数据目录，可避免与现有任务混在一起。将下列提示词交给助手：

```text
请在仓库根目录演练虚构任务卡，所有命令固定使用
python3 -m taskcard.cli --home task-cards/ai-demo
作为前缀。示例只验证本地记录流程。

先 list；如果 demo-card 尚不存在，使用
create --from examples/demo-card.json 创建它。
读取 show demo-card --json，确认目标与范围。
如果已有同名示例已完成，报告现状，不要覆盖或重新开始它。

开始执行该示例：先调用 start 并填写 note，读取并核对示例字段，
依据实际结果更新 work、记录 checkpoint、登记 evidence。
最后调用 verify；只有通过后才调用 complete，并重新读取确认状态。
报告实际执行命令和结果，不把这次演练当成完成真实业务工作。
```

`--home` 是全局参数，必须放在 `list`、`create` 等子命令前。切换会话后也必须使用同一个数据目录。Windows 或环境仅提供 `python` 时，将命令中的 `python3` 替换为可用的 Python 3 命令。

## 第三步：建立真实任务

可先向助手说明：

```text
请根据我描述的目标，参考 examples/demo-card.json，
在 task-card-specs/ 中准备一份新任务规格。
先梳理目标、当前已知事实、工作项、限制、资源、授权边界和验收条件，
对影响执行的缺失信息向我核实。不要把推测写成已确认事实。
先让我审阅规格，未授权前不要执行实际任务。
```

规格确认且准备执行后，使用 `status: "ready"` 创建任务卡，例如：

```bash
python3 -m taskcard.cli create --from task-card-specs/my-task.json
python3 -m taskcard.cli show <任务卡ID> --json
```

把 `<任务卡ID>` 替换成真实 ID；该占位符不能原样执行。讨论中的内容可先保存在规格文件，当前 CLI 没有把已有 `draft` 卡转换成 `ready` 的专用命令。

之后用户可以明确提出：

```text
开始执行任务卡 <任务卡ID>，使用之前约定的数据目录。
先重新读取完整任务卡并调用 start 记录当前环境。
按 AGENTS.md 和我的授权执行，每个阶段记录真实结果与核验证据。
涉及需要人工确认的操作，先创建审批请求并暂停，不能自行批准。
verify 通过且 complete 成功后才报告任务卡完成。
```

恢复任务时使用“继续执行”，要求助手重新读取卡片、检查实际环境并调用 `continue`。任务卡保留的是显式写入的状态与记录，并不自动保存全部聊天历史或给新助手授予旧会话的外部操作权限。

## 人工审批怎样进行

助手用 `request-approval` 记录具体动作、影响和关联工作项后，应在聊天中说明等待用户确认。用户在聊天中明确同意或拒绝，或亲自在终端执行 `approve` / `reject`；确认后才能据实写入审批结果。

当前网页仅展示待审批内容，没有审批按钮。CLI 不验证审批人的身份，因此 AI 不能用自己的判断冒充用户授权。审批获准也不会自动执行外部操作，需要助手重新检查当前情况后继续工作。

## 数据与能力边界

- 任务卡保存在本地；若外部 AI 助手使用云端模型，它读取的内容可能被发送给对应服务。实际数据处理取决于助手配置，“本地保存”不等于“推理完全离线”。
- `.gitignore` 用于避免本地记录进入常规 Git 提交，不能限制 AI 读取，也不能控制模型服务的数据处理。
- 操作浏览器、邮件、聊天软件或其他项目，依赖用户另行提供的工具与授权；本程序没有内置这些连接。
- 本程序没有后台调度器、模型调用循环或失败后自动恢复执行能力。关闭助手后，任务记录仍在，但任务不会由本程序继续执行。
- `evidence` 保存操作者登记的证据，`verify` 检查记录是否满足程序条件。AI 和人仍需检查实际产物，不能将状态检查当成业务真实性认证。
- 本地网页无登录控制，默认监听 `127.0.0.1`，应保持本地访问。避免多个助手同时写入同一任务卡。

发布时可以这样介绍：

> 这是一个供人和 AI 助手共同使用的本地任务状态工具。用户自行接入具备文件和终端操作能力的 AI 助手，通过 CLI 读取任务、执行工作并记录证据；程序保存状态、审批与执行记录，网页提供只读查看。项目本身不内置模型，AI 账号和运行环境由用户准备。
